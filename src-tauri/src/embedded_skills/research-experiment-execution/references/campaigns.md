# Local parallel campaigns

Use `.research/tools/campaign.py --root PROJECT` as the shared campaign interface. Send one JSON request on stdin and read its JSON reply. For routine agent requests include `compact: true`: the reply keeps the 20 most recently finished attempts, accepted best, reference baselines, five queued previews and up to 20 active attempts, with exact counts and omittedAttemptCount. Use `inspect` with `id` to fetch a specific attempt, or omit compact only when full state is necessary. This avoids repeatedly sending thousands of records into model context. Lattice starts the project service when the tracker is open. For command-line work start the bundled script with `--serve --owner PARENT_PID` and keep that owner alive for the campaign. Inspect before creating or resuming work.

For automatic continuation, bind the campaign to the active Lattice agent conversation with `attach-agent` and its observed `threadId`. The host sends one continuation per decision revision only while that same conversation is idle.

Every mutation includes a unique `operationId`. Reusing it safely retrieves state. Omit `budgetSeconds` when the user supplies no time limit: the campaign has no elapsed cutoff, and its deadline, budget and remaining seconds are null. The agent decides when to finish from the results. Create the campaign immediately before computational setup. Keep campaign identity independent of chat turn IDs. Paid compute and remote scheduling still require authorization.

Create using `{"action":"create","operationId":"create-1","workers":2}`. Supply a positive `budgetSeconds` only for an explicit user time limit. Such deadlines include setup, validation and reporting and persist across pauses and restarts. Never silently extend them. Optional `attemptLimit` caps attempts. Run `resume` to dispatch queued attempts. `pause` stops dispatch while active work finishes. `stop` terminates active work. `reconcile` records abandoned work and requires resume. `extend` revises an existing deadline only with authorization. `complete` records a final `reason` after work is closed.

After each bounded batch, inspect validated progress and record the next decision. Continue when a specific next experiment can improve the result or resolve a meaningful uncertainty. Finish when the stated goal is met, useful approaches are exhausted, repeated non-improvements leave no justified next test, or a blocker cannot be resolved within the available resources. A plateau calls for reassessment, not blind retries or automatic termination. Record the stopping reason and limitations, verify the selected result and finish the report. No campaign deadline does not remove per-run and verifier timeouts, Stop, or shutdown cleanup.

Register each evaluation with `action: evaluation` and an `evaluation` object containing `id`, `metric`, `unit`, `direction` (`lower` or `higher`), `baselineId`, `files`, `command`, `seconds`, and optional nonnegative `tolerance`. Files include evaluator source and fixed inputs. Their hashes freeze this evaluation. The command is an argv array executed from a fresh evaluator snapshot. `{artifacts}` expands to the attempt evidence folder and `{result}` to a fresh output path. Write JSON with Boolean `accepted`, finite numerical `score` and optional `reason`. Setup verifiers need only `accepted` and `reason`; setup validation never enters score rankings. Collect repeated measurements in the worker and save them as evidence. The evaluator checks and aggregates those saved measurements under the declared policy. Verification retries must not rerun measurement. Never modify evaluator semantics while reusing its ID.

Enqueue with `action: enqueue`, `id`, `title`, `nodeId`, `evaluationId`, `kind` (`setup`, `baseline`, `candidate`), `command` argv, positive `seconds`, `sourceFiles`, and `artifacts` relative to the attempt evidence folder. Include `gitCommit` for a Git worktree. Without it the coordinator copies declared source files into an isolated snapshot. Include parentAttemptId for the actual candidate used to construct this attempt, and identify its saved artifact or parameter state in the note. A previous result that merely inspired the next method is a decision link, not automatically the seed parent. Use retryOf only for a new measurement retry. `plan` provides initial Markdown note content. Workers write artifacts into `DEXTER_ARTIFACT_DIR` and progress events to `DEXTER_CASE_EVENTS`.

Baseline and candidate attempts include `setup: {record: "setup/environment.json", files: ["requirements.lock", "inputs/reference.json"]}`. The record must be ready with successful smoke evidence; readiness does not require a baseline. A baseline uses its own evaluation's `baselineId`. Candidates require its passed validation. Setup attempts are available before the baseline to avoid recursion. Include every writable dependency required by the invocation in the isolated workspace. Shared external interpreters must use a prepared immutable environment.

The coordinator verifies completed setup, baseline and candidate attempts separately. A command exit alone is provisional. Request `verify` with the existing attempt ID to repeat validation without repeating the measurement. Each validation receives a new numbered receipt. Rejected and failed attempts remain evidence. The latest passed result provides baseline-relative outcome and whether it was retained as best. Equal scores retain the earlier best.

Read `inspect` for remaining budget, best candidates, active attempts, repeated failures and branch plateau counters. At five valid non-improvements reconsider the branch and record the decision with `reassess`, `nodeId` and `reason`. Two matching infrastructure failures require a successful setup check before further dependent attempts. For explicitly timed campaigns only, the final 20% of elapsed budget, capped at five minutes, is reserved for validation and reporting.

Keep one note per meaningful attempt. A numerical sweep can contain thousands of candidate proposals recorded in structured artifacts. Update the existing mind map, journal and main.tex at decision boundaries. Final validation checks the selected saved bytes, then compile and inspect the PDF. Record scientific validation and document build results separately.

Worker resource records contain observed child CPU seconds and peak child RSS. They are measurements, not hard memory fences. `cpuSlots` reserves campaign worker slots and sets common BLAS/OpenMP thread counts for a workload. Kernels that ignore these environment settings remain responsible for their declared concurrency.

## Decision and record ownership

Inspect before each batch. Use observed setup and baseline costs to choose small per-run `seconds` and a bounded batch within any remaining explicit search window. After results, record the scientific decision in the note and manuscript, then enqueue the next useful batch or complete the campaign. The five-valid-non-improvement trigger is a reminder to reconsider; important contrary evidence can require reassessment sooner. Keep the same campaign across batches.

The coordinator owns campaign state, run/validation receipts, queued fields, measured scores and best promotion. The agent owns authored notes, map and manuscript. A planned journal entry may be written before enqueue, while dispatch is paused. Do not concurrently rewrite experiments.json while the service updates it. During execution put interpretation in experiment.md; update optional journal prose only after work is quiescent, re-reading and atomically preserving current fields.
